# R&D — audit de sécurité et feuille de route du site M.R.S.C

**État au 12 octobre 2026.** Audit de code du dépôt local, complété par des tests de non-régression déterministes. Les mesures CI/CD, de plafonnement des sources et d’échappement de la provenance ont été ajoutées le 12 octobre 2026. Ce document ne certifie ni l’hébergement en production ni le dépôt Render distinct. Il distingue les défauts observés dans le code, les mesures ajoutées ici et les vérifications qui restent nécessaires.

## Synthèse exécutive

Le site contient déjà des choix de conception favorables : pas de compte, de formulaire d’exercice, d’outil analytique ou de pixel publicitaire repéré dans les fichiers examinés ; parcours d’apprentissage progressif ; sources et limites éditoriales visibles ; repli explicite du simulateur ; contrôles de contraste et de reflow présents dans les vérifications statiques.

Le risque le plus important trouvé dans la copie locale du simulateur concernait les lectures envoyées par le navigateur : leur provenance était contrôlée par le client, elles pouvaient rejoindre un cache réutilisé par d’autres requêtes, puis plusieurs champs étaient rendus dans des fragments HTML. Le chemin de code pouvait donc produire une contamination persistante et une injection HTML si une donnée hostile atteignait ces champs. Le correctif local valide désormais chaque lecture contre le registre, remplace les métadonnées client, garde la mesure dans le seul contexte de la requête et échappe les champs utilisés par les vues examinées. Un test de non-régression vérifie les cas XSS ciblés ; aucun exploit navigateur contre le service public n’a été exécuté.

Les correctifs ciblés, leur patch reproductible et les tests sont présents. **Le service Render actif n’est pas corrigé par les changements de ce dépôt** : son code vit dans un autre dépôt. GitHub Pages n’exécute pas le moteur Python. La CSP configurée dans `vercel.json` ne s’applique qu’à Vercel et ne constitue pas une CSP stricte pour le JavaScript en ligne du simulateur.

## Périmètre et niveau de preuve

Examinés dans le dépôt : pages HTML/CSS/JavaScript, fiches d’apprentissage, scripts de navigation et de préférences, moteur Python du simulateur, routes serverless `api/`, pont WSGI, serveur d’aperçu local, générateur de la page publiée, provenance, configuration Vercel et workflows GitHub Actions.

Les contrôles couvrent le code présent et des services HTTP locaux simulés. Ils ne comprennent pas de scan authentifié, de test de charge, d’analyse du DNS ou des journaux des prestataires, de test avec lecteur d’écran, de test dans un vrai navigateur automatisé, ni d’observation réseau de Render, Vercel ou GitHub Pages. Une absence de résultat dans le dépôt ne prouve pas l’absence de traitement chez un hébergeur.

## Constats et traitement

| ID | Constat et preuve | Mesure dans ce dépôt | État / réserve |
| --- | --- | --- | --- |
| S-01 | **Contexte de données navigateur contaminable.** L’ancienne route fusionnait les lectures reçues dans un cache commun et acceptait des champs de provenance du client. Ce chemin pouvait faire réutiliser une lecture forgée par une requête ultérieure. | `simulateur/dashboard.py` valide clé, URL, valeur et marqueurs ; la provenance vient du registre ; le contexte est copié et propre à la requête. `simulateur/donnees_live.py` écarte les anciennes entrées navigateur lors du chargement du cache. | Corrigé localement et couvert par tests. Vérifier encore les données déjà présentes dans le cache du service Render avant d’y appliquer l’équivalent. |
| S-02 | **Injection HTML potentielle par des métadonnées de lecture.** Les vues du simulateur utilisent de nombreux sinks `innerHTML`. Les champs de lecture étaient une entrée contrôlée par requête ou source. | Échappement des champs dynamiques de provenance, liens limités à HTTPS sans identifiants, périodes/qualités/dates normalisées côté serveur et échappées au rendu ; les valeurs externes des vues examinées passent par `echapperTexte()` ou `textContent`. | Réduction ciblée et contrôles statiques/de non-régression ; pas d’exécution DOM réelle ni d’audit exhaustif de chaque template. Les handlers inline compliquent l’ajout d’une CSP stricte ; poursuivre la revue des sinks recensés dans `simulateur/interface.py`. |
| S-03 | **Corps POST sans borne applicative.** Les routes Python lisaient la longueur annoncée avant de désérialiser le JSON. | Limite de 1 Mio, rejet des longueurs dupliquées/incohérentes et de `Transfer-Encoding` non pris en charge, réponse 413 et fermeture de connexion ; la même borne existe dans `simulateur/wsgi.py` et dans le relais local. Ce dernier borne aussi les réponses API à 16 Mio. | Tests HTTP et WSGI locaux réussis. Les limites du serveur frontal et du runtime d’hébergement restent à confirmer. |
| S-04 | **Collectes réseau déclenchables à distance et répétables.** Un paramètre GET permettait de demander une collecte complète ; les routes de cotation et de relais pouvaient aussi provoquer des requêtes sortantes. | Les GET de contexte/simulation utilisent cache ou références et n’honorent plus `refresh=1` pour lancer une collecte complète. Le relais n’accepte qu’une clé du registre, met les lectures en cache 60 s et renvoie 503 sans attendre si une collecte est déjà en cours ; les rafraîchissements de marchés sont limités à un par minute et les requêtes concurrentes échouent vite, par processus. | Réduction du coût par instance, **pas** un quota global : les caches mémoire sont éphémères et un hébergeur serverless peut créer plusieurs instances. Un WAF/rate limit de bordure reste recommandé. Le rafraîchissement manuel des marchés est conservé. |
| S-05 | **Sonde de source distante configurable.** L’ancienne sonde suivait une adresse issue d’une variable de déploiement ou du HTML, sans filtrer les hôtes ni les redirections. Une mauvaise configuration pouvait transformer la sonde en requête vers un service interne. | `api/verifier-source.py` limite l’hôte de production, accepte les hôtes HTTPS de préproduction seulement sur liste explicite, refuse identifiants, chemin, query, port inattendu et redirections ; l’exception localhost exige `SIMULATEUR_SOURCE_DISTANTE_TEST_LOCALE=1`. Le paramètre public `refresh=1` ne contourne plus le cache de cinq minutes. | Tests locaux réussis. Protéger les variables d’environnement et maintenir la liste d’hôtes lors d’un changement d’hébergement. |
| S-06 | **Risque de publication involontaire par le serveur local.** Servir la racine entière d’un dépôt exposerait potentiellement des fichiers de travail ou des sources. | `outils/serveur-local.py` n’autorise que les pages, ressources, fiches et fichiers publics prévus ; refuse les chemins internes et liens symboliques qui sortent de la racine ; aucun listing de dossier ; bind `127.0.0.1` par défaut. | La whitelist est exercée en test unitaire. L’option `--bind 0.0.0.0` expose volontairement l’aperçu au réseau local : ne l’utiliser qu’en connaissance de cause. |
| S-07 | **Détails d’exception exposés.** Plusieurs routes renvoyaient le traceback dans le JSON. | Réponses internes génériques ; journalisation facultative côté moteur (`SIMULATEUR_LOG_ERREURS`) ; réponses WSGI génériques ; erreurs du relais local moins détaillées. | Test de réponse 500 sans traceback passé. Vérifier les règles de conservation et d’accès aux journaux de chaque hébergeur. |
| S-08 | **En-têtes de défense en profondeur incomplets dans la configuration Vercel.** | `vercel.json` ajoute `nosniff`, `Referrer-Policy`, HSTS, `X-Frame-Options`, `Permissions-Policy` et une CSP de base (`base-uri`, plugins interdits, formulaires même origine et `frame-ancestors`). | Applicable uniquement à Vercel. GitHub Pages et l’application Render ont leurs propres réponses. La CSP ne définit volontairement pas `script-src` : l’interface comporte des scripts et handlers inline et reste à refactorer avant une politique stricte. |
| S-09 | **Surface de requête publique et disponibilité.** Les simulations sont publiques et certains calculs (bulles, comparaisons) sont lourds ; le code local n’implémente pas un quota distribué ni un circuit-breaker commun à toutes les instances. | Taille du corps bornée, cache de calcul existant, mise en cache des lectures externes et refus rapide des appels concurrents ; limites de durée/mémoire déjà déclarées dans `vercel.json`. | Test de charge et de concurrence non effectué. Régler des quotas/caches de bordure, timeouts, nombre de threads et alertes à partir des métriques réelles. |
| S-10 | **Vie privée et services tiers.** Le code local ne montre pas de compte ni d’analytics ; préférences et navigation sont stockées dans le navigateur, la carte Google attend une action, et le simulateur transmet des requêtes aux API publiques selon les actions. | Notice publique et inventaire technique déjà présents ; lectures navigateur du correctif local non persistées dans le cache partagé. | Qualification juridique du stockage, durée des journaux, sous-traitants, traceurs après activation de Google et traitement de la version Render à confirmer par l’association et les prestataires. La présente revue n’est pas un avis juridique. |
| S-11 | **Chaîne CI/CD perfectible.** Les actions GitHub étaient référencées par des tags majeurs mutables et aucune suite générale ne bloquait les pull requests. | Actions épinglées sur des SHA vérifiés ; `.github/workflows/verification.yml` exécute compilation, contrôles statiques, sécurité et intégration sur PR et `main`, avec permission `contents: read` ; Dependabot propose les mises à jour d’actions. | La protection de branche et l’exigence de réussite du statut CI doivent être activées dans les paramètres GitHub du dépôt ; cela ne peut pas être garanti par les fichiers du dépôt seuls. Relire les propositions Dependabot avant fusion. |
| S-12 | **Réponses des fournisseurs non bornées et redirections suivies.** `donnees_live.py` et le collecteur Yahoo des cotations lisaient leurs réponses sans plafond et suivaient les redirections ; le navigateur n’avait pas de limite de taille ni de délai. Une source publique défaillante pouvait consommer trop de mémoire ou prolonger une collecte sans fin. | Sources macro côté serveur : 8 Mio maximum (+ 1 octet de détection), sans redirections, valeurs finies et bornées selon l’unité. Cotations Yahoo : 1 Mio maximum (+ 1 octet de détection), sans redirections, nombres non finis rejetés. Navigateur : redirections refusées, JSON en flux plafonné à 8 Mio, 8 s par requête et 60 s par cycle. | Plafonds serveur testés avec réponses simulées ; garde-fous navigateur vérifiés statiquement et syntaxe JavaScript contrôlée. Aucun test réel de navigateur ou fournisseur n’a été exécuté. Toute mise à jour amont doit conserver ces protections et le patch doit être revalidé. |
| S-13 | **Sink XSS dans le sous-titre de contexte.** La période de provenance de la série « nouveaux crédits habitat », issue d’une lecture externe, était interpolée dans le sous-titre de `renderContexte()` avant insertion par `innerHTML`. Les périodes, dates et libellés qualité des autres lignes de provenance étaient également interpolés directement. C’est un défaut de neutralisation démontré par lecture du code, pas un exploit observé en production. | Échappement du texte de chaque métrique, période, date et qualité avec `echapperTexte()` ; validation stricte des périodes et codes qualité, normalisation des dates de cache, reprise du fournisseur/URL depuis le registre ; contrôle statique dédié et cas de non-régression cache/provenance. | Corrigé dans cette copie locale et vérifié par contrôles déterministes/statique. Aucun essai DOM dans un navigateur réel ; le déploiement Render séparé n’est pas modifié. |
| S-14 | **Rafales sur les routes à paramètres et calculs coûteux.** Les chaînes de requête n’avaient pas de plafond applicatif ni de nombre maximal de champs. `/api/bulles` pouvait recevoir des clés répétées, et deux requêtes manquant simultanément le cache pouvaient recalculer en parallèle l’ensemble des bulles (plusieurs secondes selon la mesure du code). | Cible HTTP limitée à 16 Kio, parsing limité à 128 champs, sélection de leviers bornée à la taille du catalogue et dédupliquée ; un seul calcul bulk de bulles par processus, les concurrents reçoivent HTTP 503. Le pont WSGI refuse une cible trop longue avant de la reconstruire en mémoire. | Tests HTTP/WSGI locaux réussis. Caches et verrouillage restent par processus ; cela ne remplace pas un quota ou rate limit CDN distribué ni un test de charge. |

## Contrôles exécutés

Résultats reproductibles dans l’environnement de travail :

- `python3 -m py_compile simulateur/*.py api/*.py outils/*.py` : compilation de tous les modules Python réussie.
- `python3 outils/construire-apprentissages.py --verifier` : 70 fiches et 15 domaines, sorties générées synchronisées ; contrôle de forme, non relecture pédagogique.
- `python3 outils/verifier-site-statique.py` : 82 pages HTML, 70 fiches, 81 URL du sitemap, scripts/liens locaux, limites navigateur et échappement des périodes/dates/qualités de provenance contrôlés ; vérification statique, pas test navigateur.
- `python3 outils/verifier-securite.py` : **59 contrôles ciblés passés**, sans réseau externe : réponses macro/Yahoo bornées, limites de cible/champs de requête, calcul de bulles anti-rafale, redirections refusées, provenance et cache neutralisés, injection XSS ciblée, isolation du contexte navigateur, limites HTTP/WSGI, erreurs génériques, cache des relais, allowlist SSRF, patch local, whitelist statique, conformité Vercel, actions épinglées et CI PR.
- `python3 outils/verifier-integration.py` : **tous les contrôles passent** ; la page générée, les 16 routes, 70 fiches, les liens/repères/scripts et les fonctions sont vérifiés. La source Render est remplacée dans ce test par un serveur factice localhost, pas par l’adresse de production.
- `python3 outils/construire-simulateur.py --verifier` : page publiée à jour.
- Patch vérifié contre la révision amont exacte `99491d872f1fb2716041aeb4733f5921359ec7c6` dans une copie temporaire propre : application réussie et cinq fichiers moteur identiques octet pour octet à la copie auditée. Le test de non-régression vérifie aussi le retrait/réapplication du patch et la copie des sources conservées.

Non exécutés : Playwright/Selenium, exploitation dans un vrai navigateur, tests avec clavier/lecteur d’écran, audit réseau public, fuzzing, charge distribuée, scan de dépendances externe et audit du Render réellement déployé. La réussite des contrôles ci-dessus ne vaut pas pentest ni certification.

## Feuille de route priorisée

### P0 — avant d’annoncer le moteur « sécurisé »

1. **Reporter le patch dans le dépôt qui héberge réellement Render**, puis vérifier le commit amont, l’environnement de cache, le bind/port et les en-têtes. La copie de ce dépôt ne modifie pas le service public.
2. Déployer un aperçu Vercel contrôlé et vérifier sur les réponses réelles l’application des en-têtes, le comportement des 16 routes, l’iframe, les erreurs 413/500 et la limite des lectures externes.
3. Lancer une revue DOM en navigateur avec des chaînes XSS dans chaque source/champ dynamique, puis tester clavier, zoom 200 %, affichage étroit, contraste forcé et lecteur d’écran sur accueil, catalogue, fiches et simulateur.
4. Ajouter un contrôle de débit au niveau de l’hébergeur ou du CDN (IP/route, quotas et concurrence), car une limite en mémoire par instance n’est pas distribuée.
5. Faire confirmer par l’association la notice de confidentialité, les durées et destinataires ; faire confirmer par les prestataires leurs journaux et réglages réels.
6. **Activer la protection de branche dans GitHub** : exiger une revue et le statut `Vérification du site M.R.S.C / qualite` avant fusion dans `main`, et interdire les push forcés ; les fichiers du dépôt ne peuvent pas activer ces règles à la place d’un administrateur.

### P1 — défense applicative et qualité d’usage

- Remplacer progressivement les `onclick`/handlers inline par `addEventListener`, séparer CSS et scripts, puis déployer une CSP réellement restrictive adaptée à l’origine et aux intégrations. Ne pas ajouter `unsafe-inline` comme substitut à cette refonte.
- Finir l’inventaire des `innerHTML` : préférer `textContent`, nœuds DOM et attributs validés ; si du HTML riche est indispensable, utiliser une politique de sanitisation testée et réviser les URL et attributs d’événement.
- Mettre des timeouts explicites côté navigateur, annuler les requêtes devenues inutiles, exposer l’état de fraîcheur/indisponibilité sans relancer de collecte cachée.
- Tester au moins Chromium, Firefox et Safari mobile ; intégrer des tests de parcours axe/ARIA et garder une revue humaine pour les annonces dynamiques et les tableaux larges.

### P2 — performance, transparence et maintenabilité

- Mesurer LCP/INP/CLS sur vrais mobiles avant d’optimiser ; surveiller la taille de `/api/bulles` (environ 2,2 Mo non compressés dans le contrôle local), fractionner les payloads et garder les réponses calculées séparées des données fraîches.
- Versionner les snapshots de données publiques avec date, licence, période, statut et niveau de qualité ; montrer clairement « observation », « référence », « estimation » et « scénario », sans suggérer une prévision.
- Ajouter des tests de contrat pour chaque nouvelle route, un test de patch amont sur la révision candidate et un contrôle de publication qui compare les fichiers publics à une allowlist.
- Conserver une voie de fonctionnement sans JavaScript pour la mission, la navigation et les fiches essentielles ; mesurer le poids et la lisibilité avec réseau lent et zoom élevé.

## Brainstorming — un site attractif sans effet de mode

À choisir après mesures, tests avec des personnes et validation des contenus :

- **Un accueil à trois portes** : « comprendre le mouvement », « apprendre un sujet », « explorer une hypothèse », avec le même langage et un seul appel à l’action principal par écran.
- **Parcours courts et imprimables** : 5, 15 ou 30 minutes, fiches lisibles hors ligne, objectifs et correction progressive, sans compte ni suivi individuel.
- **Mode “données en clair”** : pour chaque nombre, période, source, licence, statut, date de collecte et limites ; possibilité d’ouvrir la source officielle.
- **Simulateur à deux vitesses** : une lecture simple des effets, puis un panneau expert ; afficher incertitudes, hypothèses et effets indirects, pas seulement un score.
- **Vue “qu’est-ce qui a changé ?”** entre deux scénarios, avec explication en langage courant et comparaison à la référence ; export local volontaire, sans téléversement.
- **Recherche globale discrète**, clavier d’abord, tolérante aux accents ; index local construit au déploiement, sans service de suivi tiers.
- **Mode faible débit / réduction d’animation** et option de lecture simplifiée ; préférences locales, contrôlables et documentées.
- **Registre public de maintenance** : historique des sources, dates de vérification, changements de règles et limites connues, afin que la transparence soit une fonction produit.
- **Éviter** : chatbot omniprésent sans périmètre, compte obligatoire, animations décoratives lourdes, scores de personnes, collecte d’usage par défaut, promesses de prédiction et faux indicateurs de temps réel.

## Exemple à suivre : la fiche de référence

Un écran exemplaire pour le M.R.S.C devrait tenir sur ces principes : **une intention explicite ; une hiérarchie stable ; une action principale ; des sources consultables ; une limite formulée sans jargon ; un état visible (chargement, succès, erreur) ; navigation clavier et lecteur d’écran ; reflow sans zoom horizontal ; aucune donnée personnelle demandée par défaut ; et une solution de repli si le service externe est indisponible.** Les fiches d’apprentissage autonomes et la page de transparence sont de bonnes bases de travail ; elles doivent encore être validées sur de vrais appareils et avec des personnes concernées.
